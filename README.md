## Publish with GitHub Pages

1. Authenticate: `gh auth login` (browser sign-in; do not paste tokens into chat).
2. The confirmed owner is **swiftjustice**. Authenticate with an account allowed to create and push the public repository `swiftjustice/ar-site`.
3. From this directory, after reviewing the page:

   ```sh
   git add index.html CNAME .nojekyll .gitignore README.md
   git commit -m "Add AR internal-use EULA site"
   gh repo create swiftjustice/ar-site --public --source=. --remote=origin --push
   ```

   Review all files for sensitive data before making a public repository. None should contain credentials or company records.

4. In that GitHub repository: **Settings → Pages → Build and deployment → Deploy from a branch → main → /(root) → Save**.
5. Set **Custom domain** to `ar.davidson.llc` and save. The checked-in `CNAME` file should match.
6. Ideally verify ownership first in the owner account/organization's **Settings → Pages**. GitHub provides a TXT challenge. Copy its exact name/value into DNS and keep it after verification. This helps prevent domain takeover. Do not point DNS at an unclaimed Pages site.
7. Add the public-site CNAME below. Wait for deployment/DNS/certificate provisioning, then enable **Enforce HTTPS** in Pages.
8. Check `https://ar.davidson.llc/` in a browser. Only then use it in Intuit's EULA field.

GitHub Pages permits public repositories on free plans; private repository Pages availability depends on the account plan. This site contains only deliberately public legal content.

## DNS plan

Leave existing `davidson.llc` website, mail/MX, and other records unchanged. Use separate subdomains:

| Type | Name (relative to davidson.llc) | Value | Purpose |
|---|---|---|---|
| CNAME | `ar` | `swiftjustice.github.io` | Public EULA site on GitHub Pages |
| A | `oauth-ar` | `127.0.0.1` | OAuth callback resolves to the browser user's own machine |
| TXT | Exact name supplied by GitHub | Exact verification token supplied by GitHub | Verify Pages domain ownership |
| TXT | `_acme-challenge.oauth-ar` | Generated by the certificate client | DNS-01 proof for the local callback's TLS certificate |

The CNAME target is `swiftjustice.github.io`—not `swiftjustice.github.io/ar-site` and not `github.com`.

Use DNS-only records, not a CDN/reverse-proxy mode, especially for the loopback hostname. Do not add an AAAA record for the callback unless the listener is deliberately configured for IPv6 loopback too. No router forwarding or public inbound port is needed. Some resolvers, corporate policies, or DNS-rebinding protections refuse public hostnames resolving to loopback. If that occurs, a local hosts entry `127.0.0.1 oauth-ar.davidson.llc` can supply local resolution; do not disable broad DNS security protections.

The `_acme-challenge` TXT value is **not static** and is not a secret API credential. The certificate tool supplies it during issuance/renewal; never invent it. DNS provider API tokens and certificate private keys must stay outside this public repository. Existing restrictive CAA records may need review to permit the chosen certificate authority.

## Option 1: local HTTPS OAuth callback

Proposed registered production redirect URI:

```text
https://oauth-ar.davidson.llc:8843/callback
```

Use this exact URL, including scheme, hostname, port, and path, in both Intuit and the local client. The nonprivileged port avoids running the app as root. Intuit documents HTTPS and hostname requirements; acceptance of this particular loopback-hostname/port setup has not been verified. If the portal rejects it, stop and investigate rather than assuming it is supported or trying to evade validation.

### Why DNS is not enough

A browser follows the redirect to its own machine. That machine needs:

1. A publicly trusted TLS certificate covering `oauth-ar.davidson.llc`.
2. An HTTPS callback listener on `127.0.0.1:8843` during authorization.
3. OAuth state validation and a local exchange of the authorization code for tokens.
4. Secure credential storage; no callback query-string logging, analytics, or third-party scripts.

Obtain the certificate using an ACME client's **DNS-01** challenge. DNS-01 works without a public HTTP server and does not require the callback A record to be publicly routable. HTTP-01 is not suitable for a loopback-only listener. A typical Certbot flow, once installed, is:

```sh
certbot certonly --manual --preferred-challenges dns \
  -d oauth-ar.davidson.llc \
  --config-dir "$HOME/.local/share/ar-oauth/acme/config" \
  --work-dir "$HOME/.local/share/ar-oauth/acme/work" \
  --logs-dir "$HOME/.local/share/ar-oauth/acme/logs"
```

The tool prompts for DNS TXT proof and its own account/terms requirements. Use restrictive permissions on its per-user directories. Manual DNS validation requires manual renewal unless a DNS provider plugin/hook is configured. Do not consider this production-ready without an expiry/renewal plan. The DNS API credentials for automated renewal belong in secure storage with narrowly scoped privileges, never this repository.

GitHub Pages handles the public site's HTTPS certificate separately. Its certificate/private key cannot be reused by the local callback listener. A self-signed certificate with a browser warning is not an acceptable substitute for the trusted callback certificate.

### Research CLI adaptation still required

The current `qbo-research` tool treats custom hostnames as manual-callback mode; it only starts its built-in HTTP listener for localhost/loopback redirect hostnames. Therefore **setting this DNS and redirect URI alone will not enable an automatic callback**.

For option 1 we must add an explicit local-callback mode that:

- Keeps `https://oauth-ar.davidson.llc:8843/callback` as the OAuth redirect URI for both authorization and token exchange.
- Starts an HTTP listener bound only to `127.0.0.1:8844`, plus a local TLS proxy bound only to `127.0.0.1:8843`, or directly implements HTTPS on the latter.
- Uses the issued certificate/key, validates state, suppresses callback URL logs, closes after success/timeout, and stores tokens in Linux Secret Service.
- Does not turn the app's private IPC service into an unauthenticated network API.

No TLS proxy, callback modification, or certificate is implemented in this static website repository. Development tooling/configuration for the research client belongs in the shared pinned Nix setup in `stack-top`, not in a public legal site.

Only initial authorization/reauthorization needs the local listener. API requests and refresh-token exchanges are outbound and do not require a callback server to remain running. Authorize in the browser on the same computer as the listener; a phone/browser on another computer would redirect to that other device's loopback interface.
